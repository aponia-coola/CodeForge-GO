# CodeForge-GO 对标分析：Codex CLI / Claude Code

分析日期：2026-11-11
分析范围：全仓库 27.5k 行生产代码 + 29.2k 行测试，10 个包
对标对象：OpenAI Codex CLI（Rust）、Claude Code（Node + 二进制）

---

## 一、结论先行

**CodeForge-GO 在「上下文工程」和「文件级安全」两条线上已经优于两个对标品；在「安全强制力」和「扩展点广度」两条线上有真实差距。**

| 维度 | 判定 | 一句话 |
|---|---|---|
| **安全强制力** | **Codex 更好** | 本项目是应用层软围栏，**无 OS 级强制隔离**。Codex 有 seatbelt/landlock 内核级沙箱 |
| **撤销/回滚** | **本项目更好** | 指纹 CAS + 会话分桶撤销栈 + 按步检查点，超过 Codex 与 Claude Code |
| **上下文估算** | **本项目更好** | 无 tokenizer 依赖下的在线校准机制，比 Claude Code 直接用官方 tokenizer 更通用 |
| **压缩无损性** | **本项目更好** | `sess.Messages` 永不丢历史，压缩只改送模视图；Claude Code 的 compaction 真的替换历史 |
| **大结果外置** | **本项目更好** | spill 零丢失 + 不开文件围栏洞；Claude Code 的 context editing 是有损指针 |
| **扩展点广度** | **Claude Code 更好** | 本项目**零 hooks**、MCP 只有 tools、插件只能加工具不能拦截 |
| **执行并行度** | **对标品更好** | 本项目逐条串行，**审批会冻结整轮只读调用** |
| **可观测性** | **对标品更好** | 无 `/doctor`、无 `/cost`、审计缺 session_id |

**一句话：技术底子比两个对标品都扎实，缺的是「安全强制层」和「横向扩展点」这两块结构性能力。**

## 二、P0 —— 安全与正确性真缺口

### P0-1　无 OS 级强制沙箱（本项目 vs Codex 最大的架构差距）

Codex CLI 的核心优势是 **seatbelt (macOS) / landlock (Linux)** 提供内核级文件系统隔离：
`workspace-write` 策略由内核强制，模型进程**物理上无法**写出工作区。

本项目的对应物是 `FS.checkScope`（`pkg/tools/builtin/file_ops.go:338-367`）——**两层词法校验 + 软链解析**，
本质是"程序自己检查参数"。

| Codex 能力 | 本项目 | 证据 |
|---|---|---|
| seatbelt / landlock | **无** | 全仓库无 `seccomp`/`landlock`/`bwrap`/`nsjail` |
| AppContainer / Job Object | 仅进程组管理（杀孙进程），非权限限制 | `pkg/platform/proc_windows.go:100` `CreateJobObject` 只做 `KILL_ON_JOB_CLOSE` |
| `--sandbox` 降级档 | 三态权限模式 | `pkg/security/policy.go:50-54` |
| 内核强制 workspace-write | 应用层路径校验 | `file_ops.go:338` |

**后果**：`run_command` 的 shell 命令本身没有任何 OS 级约束。
`commandTouchesOutside`（`pkg/tools/builtin/terminal.go:257-282`）是纯启发式字符串扫描，
代码注释自己承认（`:256`）：

> "shell 引用/拼接等形式的手法不在此列，最终防线是审批环节的人工确认。"

即 **Codex 的 landlock 能挡住 `cat /etc/passwd`，本项目挡不住，只能靠弹审批**。

**判定**：这是与 Codex 的**最大架构差距**，且**与轻量目标直接冲突**（landlock/seatbelt 需要系统调用，
Windows AppContainer 需要 cgo 封装）。**建议：不追**，理由见第五节。

### P0-2　命令黑名单可绕过（实测）

`pkg/security/policy.go:31-47` 的 `builtinDenyPatterns` 是纯正则，`:33` 一条：

```
(?i)\brm\s+(-[a-zA-Z]+\s+)*-[a-zA-Z]*(r[a-zA-Z]*f|f[a-zA-Z]*r)[a-zA-Z]*\s+(/\*?|\*)\s*$
```

末尾 `\s*$` 锚定是致命伤——**命令后跟任何东西就整体失配**。实测：

| 命令 | 命中 Deny |
|---|---|
| `rm -rf /` | ✅ |
| `rm -rf / ; echo done` | ❌ **绕过** |
| `rm -r -f /` | ❌ **绕过**（`-r` `-f` 是分开两个 flag，正则要求合并） |
| `rm -rf --no-preserve-root /` | ❌ **绕过** |
| `bash -c 'rm -rf /'` | ❌ **绕过** |
| `echo <base64> \| base64 -d \| sh` | ❌ **绕过** |

**需要澄清的两点**（避免误判）：

1. 默认 `permission_mode` 是 **`ask`**（`config/default.yaml:48`），不是 `auto`。
   `config/local.yaml:26` 的 `auto` 是**本机本地配置**，不是仓库默认值。
2. `auto` 档注释（`policy.go:170-174`）写"强制审批仍生效"——
   `approvalRequired` 机制**确实存在**（`policy.go:66,205-211`），
   但 `NewPolicy` 里它初始化为空 map（`:76`），**只有插件能往里塞**。
   所以 `auto` 档的实际语义是：**除黑名单外全部放行，插件的强制审批也被跳过**。
   这比 Claude Code 的 `bypassPermissions` 还宽。

**建议**：
1. 黑名单去掉末尾锚定（宁可误报），补 `rm -r -f` / `--no-preserve-root` / `bash -c` 包裹 / `eval`
2. `auto` 档对高危命令前缀（`rm`/`dd`/`mkfs`/`chmod -R`/`curl|sh`）**强制 Ask，不受 auto 影响**
3. 本机 `local.yaml` 的 `auto` 建议改回 `ask`

### P0-3　审批盲区：缺 DiffProvider 的工具在盲批

`pkg/tools/tool.go` 的可选接口靠**运行时类型断言**发现。实测漏实现清单：

| 接口 | 实现者 | 缺口 |
|---|---|---|
| `Metadata()` | 16 个内置工具全部 | ✅ 有 CI 护栏（`side_effect_test.go:41`） |
| `ScopeChecker` | 8 个 | ✅ |
| `DiffProvider` | **仅 2 个**（`WriteFileTool` `file_ops.go:1488`、`EditFileTool` `:1754`） | ❌ **`delete_file`**（`:1924`，声明 `SideEffectDestructive`）、**`create_skill`**（`skill_creator_tool.go:22`，声明 `SideEffectWrite`）都没有 |
| `TimeoutPolicy` | 1 个（`GoalVerifyTool`） | ✅ 合理 |

**后果**：`delete_file` 是不可逆破坏性操作，审批时**用户只能看到路径字符串**，看不到将被删掉的内容。
这正是 AGENTS.md 硬规则 3a 自己承认的「漏 `DiffProvider` = 用户盲批」。

**对比**：
- Codex：工具注册时构造完整 `ToolSpec {name, sandbox_requirements, approval_policy}`，**注册期报错**
- Claude Code：声明式权限规则文件，**用户能看到缺项**
- 本项目：运行时断言，**静默降级**

**建议（改动量最小、收益最高）**：在 `Registry.Register` 时校验——
声明了 `SideEffectWrite/Destructive` 的工具若未实现 `DiffProvider`，**拒绝注册并给出明确错误**。
把现在的 CI 护栏前移到运行时。

### P0-4　审计记录与用户会话完全脱钩

`pkg/security/audit.go:13-22` 的 `AuditEntry` 字段：

```go
type AuditEntry struct {
    Time, Tool, Action, Decision string
    Approved *bool
    Success  bool
    Error    string
    DurationMs int64
}
```

**没有 `SessionID` / `Step` / `ToolCallID`**。后果：
- 一次会话的 50 次工具调用在 `audit.jsonl` 里**无法关联到会话**
- 无法与界面上的工具卡片一一对应（界面事件 `pkg/agent/agent.go:52-77` 有 `SessionID`/`ToolCallID`）
- `Action` 字段记的是 `extractAction` 提取的第一个字符串字段（`executor.go:523-534`），
  **与界面事件里的完整 `ToolInput` 内容不同**，无法对齐

**另一处自相矛盾**：`audit.go:105-108` 的注释明确说"轮转失败**不静默**……错误上抛，由调用方决定怎么办"，
但 `executor.go` 的 **6 处调用点全部写成 `_ = e.audit.Log(entry)`**（`:218,230,265,278,300,317`）——错误被全部丢弃。
**审计写入失败 = 完全无痕**，这与"审计作为安全凭据"的定位直接冲突。

## 三、P1 —— 明确收益的架构改进

### P1-1　ExecutionRecord：把三处割裂合成一处（AGENTS.md 自认未落地）

AGENTS.md §5 写「每次工具调用一条权威 `ExecutionRecord`，审计、界面事件、检查点都从它派生」——
核实结果：**代码里零实现**（`grep ExecutionRecord` 只命中 AGENTS.md 那一行）。

现状是三处各记各的：

| 处 | 记什么 | 缺口 |
|---|---|---|
| 审计 JSONL | `Tool/Action/Decision/Approved/Success/Error/DurationMs` | 无 session_id、无完整 args |
| 界面事件 WS | `Type/SessionID/ToolCallID/ToolName/ToolInput/Decision/Reason/Result/Diff` | 无 step、无副作用等级 |
| 检查点 SQLite | `SessionID/Step/Path/Existed/OldContent` | **完全无决策信息**（不知是否经审批） |

**更要紧的是：策略被判定了两次。**
- `pkg/agent/agent.go:1307` `a.executor.Evaluate(tc.Name, tc.Input)` —— 给界面显示用
- `pkg/tools/executor.go:210` `e.decide(tool, name, action, args)` —— 给实际执行用

两次判定之间策略可能已热切换（`/api/perm` 支持热切换，`pkg/server/api_handlers.go:68`），
**界面显示的决策与实际执行的决策可能不一致**。

**这是"权威记录"要解决的核心问题——它不只是少一个类型，而是一个已经存在的行为不一致。**

### P1-2　工具逐条串行 + 审批冻结整轮（性能与体感双输）

`pkg/agent/agent.go:1304-1344` 的循环：

```go
for _, tc0 := range turn.ToolCalls {
    res, _ := a.executor.Execute(toolCtx, tc.Name, tc.Input)   // :1333 阻塞
    sess.appendMessages(...)                                     // :1339 逐条
}
```

**没有并发度控制**。尽管 `pkg/tools/tool.go:82-84` 的注释明确说 `ConcurrentSafe` 字段被推迟是因为
"批量并发调度属 2.6（ReAct 循环状态化）"——**即 `SideEffect` 已经分好级
（none/write/external/destructive），但调度器完全不用它。**

**最恶劣的情形**：审批在 `executor.go:257` 阻塞等 WS 回包（超时 15 分钟）。
**一条 `run_command` 卡住审批 → 同一轮的全部只读调用（read_file/list_dir/search）全部排队冻结。**

量化：一轮 8 个大文件读取（1~5MB），串行 IO 约 0.4~4 秒纯等待；Claude Code / Codex 并行后约为 max 而非 Σ。

**这是本项目与对标品差距最大、且完全没被利用已有设计的一处。**

### P1-3　权限档缺中间态

| | Claude Code | 本项目 |
|---|---|---|
| 档位 | default / acceptEdits / plan / bypassPermissions（4 档） | readonly / ask / auto（3 档） |
| acceptEdits | 文件编辑自动放行，命令仍问 | **无对应档** |
| plan | 只读规划不执行 | 无（readonly 更严但拒绝一切写） |
| session 级放行 | 有（"allow for this session"） | **无**（grep 零命中） |

本项目的 `auto` 一档把**命令也一起放行**，比 Claude Code 的 `acceptEdits` 激进得多。

**建议**：加 `acceptEdits` 档（文件编辑自动放行、命令仍审批），并给高危命令加"本会话允许"记忆。

### P1-4　零 hooks —— 扩展点只有纵向

Claude Code 的 `PreToolUse` / `PostToolUse` / `UserPromptSubmit` / `Stop` / `SessionEnd`
可以跑任意用户脚本，能**否决工具调用**。

grep 全仓库 `hook|PreToolUse|PostToolUse|beforeTool|afterTool`：
只命中 `pkg/llm/sse.go:52-65` 的 `RetryHook`（LLM 重试回调，与工具无关）。

**结论**：本项目**没有任何等价物**。用户想"写 .go 文件前自动 gofmt"、"提交前跑 lint"，
唯一途径是改代码或包成插件——**而插件只能加新工具，不能拦截既有工具**。

本项目的扩展点是**纵向**的（加新工具），Claude Code 的是**横向**的（在既有工具链上挂钩子）。

**与轻量的关系**：进程内 Go 回调不冲突（改动量中等）；**跑用户脚本版与轻量冲突**（需要沙箱）。

### P1-5　MCP 只有 tools，没有 resources/prompts

`pkg/tools/plugins/driver_mcp.go:71` 的 initialize **上报空 capabilities**：

```go
"capabilities": map[string]any{},
```

且 grep `resources/list|prompts/list|resources/read` 在 `pkg/tools/plugins/` 下**零命中**。

**后果**：装了 MCP server 只能用到它的 tools，server 暴露的 **resources（文档库、schema）
和 prompts（代码审查模板）完全拿不到**。

传输层（stdio/http/SSE/WASM）已完备，**纯客户端代码，不与轻量冲突**。

### P1-6　插件工具不参与围栏，且一律按破坏性处理

`pkg/tools/plugins/loader.go:27-48` 的 `RemoteTool` **没实现 `Metadata()`**：
- `MetadataOf` 返回 `ok=false` → `SideEffectFor` 返回 `SideEffectDestructive`
- → **所有 MCP/HTTP/WASM 插件工具在只读模式下一律被拒**（fail-closed，方向正确）
- → 在 ask 模式下**全部按 destructive 走审批**，审批文案无区分
- → 也**没实现 `ScopeChecker`** → **插件工具不参与工作区围栏检查**
  （`executor.go:165` 断言失败 → `outOfScope=false`），越界只能靠插件自己声明 `requires_approval`

### P1-7　缺 `/doctor` 与 `/cost` 等价物

36 条路由里**没有一个是诊断命令**（`pkg/server/server.go:157-194`）。

| 命令 | Claude Code | 本项目 |
|---|---|---|
| `/context` | 逐文件 token 明细 + 压缩历史 | **有**（`contextUsage`）但只有聚合数字，无按来源分解 |
| `/cost` | 累计花费 | **无**（有 token 数但无单价配置、无换算、无按会话累计） |
| `/doctor` | 环境诊断、MCP 连通性体检、hook 配置检查 | **无** |

**`/doctor` 的价值特别实在**：现在 MCP 插件加载失败只 `logx.Errorf` 并计入 `LoadAll` 的 errs
（`pkg/tools/plugins/manager.go:46-48`），**进程继续跑，用户界面上没有任何提示哪个插件没加载上**。
`handleHealth` 只报 `len(s.registry.Names())`（`pkg/server/api_handlers.go:84`），
不报**哪些工具因安全声明被降级**、哪些插件工具缺 `Metadata`。

**这是把"静默降级"变成可见的最低成本手段。**

## 五、轻量级取舍 —— 哪些不该追

这是本报告最重要的一节。**对标差距不等于都该补。**

### 5.1 因轻量而合理放弃的（不建议追）

| 能力 | 为什么放弃是对的 |
|---|---|
| **LSP 集成** | gopls 冷启动 1~3s、RSS 100MB+。**与 25 MB 常驻直接冲突**。没有 LSP 不是缺陷，是产品定位 |
| **常驻 AST 索引** | 需要持久化索引 + 常驻内存。同上。但可用「一次性 `go/parser` 解析」替代（改动量中） |
| **真实 tokenizer 内嵌** | 会引入依赖。**但本项目已用在线校准补齐**（`pkg/agent/history.go:263-305`：拿到上游真实 usage 算比值、只放大不缩小、落盘 `token_factor`）。**这比塞个 tiktoken 更通用** —— 任何上游的真实 usage 都能当校准源 |
| **本地视频抽帧** | 需真解码器，标准库没有。与 `CGO_ENABLED=0` 冲突。AGENTS.md 硬规则 16d 已明确定位 |
| **OS 级沙箱（landlock/seatbelt/AppContainer）** | 见 5.3 |
| **多实例/多进程** | 单实例为主，`-resume` 另开只读连接。符合"个人工具"定位 |

### 5.2 与轻量**无关**、属真短板的（应该补）

第 P2 节里的 1~6 号全部属于此类：
**microcompact、会话导出、子智能体 markdown、上下文分解、只读 git 工具、检查点上限**
——它们要么是纯数据层改动，要么复用现成代码，**不增加常驻内存、不引入依赖、不破坏 `CGO_ENABLED=0`**。

**这类才是最值得优先做的改进**——它们同时满足"补齐对标差距"和"不破坏轻量"。

### 5.3 关于 OS 级沙箱：我的明确建议是**不追**

Codex 的 landlock 是它作为"云端跑模型、模型可能恶意"这个场景的**必要条件**——
它的模型在云上，代码在本地，中间是威胁模型。

**CodeForge-GO 的威胁模型不同**：模型跑在用户自己的机器上，用户自己发的指令，
审批卡片就在用户眼前。**用户是信任的最终裁决者**——这不是安全模型的缺陷，是场景差异。

所以：
- 补 landlock 会引入 cgo / 系统调用，**直接破坏 `CGO_ENABLED=0` 与单文件静态二进制**这两个产品立意
- 而它要防的场景（模型绕过审批恶意写系统目录）在本项目的部署形态下**威胁等级低得多**

**结论：保持现状，把力气花在 P0-2/P0-3/P0-4（应用层加固）+ P2 的小改动上。**
**并且要在 README 里把这一点说清楚**——"本项目无 OS 级沙箱，安全性依赖审批环节的人工确认"
比含糊其辞更能建立信任。

## 六、本项目优于对标品的三处（面试时值得主动讲）

### 1. 估算器在线校准（`pkg/agent/history.go:263-305`）

在**无 tokenizer 依赖**的约束下，用上游返回的真实 usage 反推校准系数，
且**只放大不缩小**（宁可早压——压缩幂等，漏压的代价是整轮失败），
**且落盘**（`sessions.token_factor` 列）——专门解决"每次启动第一次就炸上下文"。

配套：压缩状态三列全落盘（`compressed_up_to`/`summary_text`/`token_factor`，
`pkg/store/store.go:102-122`）。Claude Code 的 compaction 是有损且不可复现的，
本项目把"摘要不可复现"这件事认识得很清楚。

### 2. 压缩永不丢历史（`pkg/agent/agent.go:488-609`）

`sess.Messages` 永远是完整历史，压缩只影响"送模视图"（`requestView`）。
用户回看、Regenerate、界面回放都拿到完整对话。**Claude Code 的 compaction 会真的替换历史内容。**

### 3. 撤销/回滚的粒度

指纹 CAS + 会话分桶撤销栈 + 按 ReAct 步的检查点（`pkg/agent/checkpoints.go`）。
Claude Code 的 checkpoint 是 git stash 风格的整体回退；
本项目能按 (会话, 步, 路径) 三元组精确回滚，且**子智能体围栏不可被审批穿透**
（`pkg/tools/builtin/subagent_fence_test.go:78-84` 的 `TestSubagentFenceSurvivesApproval`
直接钉住这条不变量）。

**这条不变量测试比 Claude Code 的权限模型更严格，值得单独讲。**

## 八、一句话

> **技术底子比 Codex 和 Claude Code 都扎实**——上下文校准、无损压缩、文件级撤销、子智能体围栏这四处
> 做得比它们更严谨。**真正缺的是两件结构性能力**：OS 级安全强制（**建议不追**，与轻量立意冲突且
> 威胁模型不同）和横向扩展点（hooks / MCP resources，**建议追**，传输层已就绪）。
>
> **性价比最高的路径不在"补大功能"，而在把已有的能力"补齐口径"**——
> 审计加 session_id、注册期校验元信息、黑名单去锚定、并行调度用上现成的 SideEffect 分级。
> 这些一条依赖都不加，却能让"看起来专业"变成"确实专业"。
