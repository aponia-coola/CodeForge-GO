# CodeForge-GO 求职差距评估

评估日期：2026-11-11
评估对象：`raine-x/CodeForge-GO`（公开仓库），源码 `Desktop/Code/CodeForge-GO/`

---

## 一、总体结论

**代码本身已经够格，缺的是"让陌生人在 30 秒内信任它"的工程包装层。**

这是本次评估最重要的判断，必须放在最前面：

- 技术底子**扎实**：27.5k 行生产代码 + 29.2k 行测试、10 个包、138 个测试文件、
  核心包覆盖率 76%~87%、4 个直接依赖、三平台静态编译、91 次提交。
- 但**面试官看不到这些**。他们点开 GitHub 看到的是：2 star、无 CI 徽章、
  无 Releases 展示、License 识别为 `NOASSERTION`、无 topics、无 profile README。

求职失败通常不是"代码不够好"，而是**证据链在"工程可信度"这一环断了**。

### 差距分布

| 维度 | 现状 | 求职影响 | 优先级 |
|---|---|---|---|
| **CI** | **无任何 CI 配置**（无 `.github/`） | **致命**：文档反复宣称"CI 绿灯"但无从验证 | P0 |
| 可见性 | GitHub 2 star / 0 fork / 0 issue；无 topics | 高：仓库无标签等于没分类 | P0 |
| 开源合规 | `license: NOASSERTION`（GPL-3.0 + 自定义条款） | 中高：企业法务/开源岗会卡 | P1 |

| 发布节奏 | 7 个 tag、1 个 Release，但版本命名不统一（`v0.1.0` 与 `预览版` 混用） | 中 | P1 |
| 真实缺陷 | `s.cfg` 无锁竞争、黑名单可绕过 | 中高：技术深挖会暴露 | P1 |

## 二、P0 —— 必须修，否则直接减分

### P0-1　没有任何 CI

**证据：**
- 仓库内**不存在** `.github/` 目录，无任何 workflow 文件
- 但 `AGENTS.md:43` 写"漏声明直接 CI 红"、`AGENTS.md:46` 写"违规直接 CI 红"、
  `Makefile:78` 写"这一整类缺陷在 CI 上全程绿灯"——**这些断言从未被自动执行过**
- 好消息：那个长期 FAIL 的测试（`TestDescribeTreeReadErrorHintsTermuxStorage`）
  已修复（`403a3e6`，平台判定改为显式传参），**现在 `go test ./...` 全绿**，
  CI 建起来就能直接通过

**动作：** 加 `.github/workflows/ci.yml`：
- Go 1.25 矩阵（windows + ubuntu）跑 `gofmt -l` / `go vet` / `go test ./...`
- 三个前端测试（`render_md.test.js` / `attachments.test.js` / `picker.test.js`）
- 三平台交叉编译验证
- **注意**：`pkg/tools/builtin` 在全量并跑 + 覆盖插桩时会撞 Go 默认 10 分钟超时，
  该包需单独 `-timeout 20m`（实测 39s 通过 / 74.7%）

README 顶部加 build + test 徽章。

### P0-2　仓库没有 topics，star 数 0

GitHub API 返回 `topics: []`。仓库不填 topics 就不会出现在任何"Go + AI Agent"相关的检索里。

**动作：** 加 topics：`go` `ai-agent` `llm` `agent` `code-generation` `sandbox`
`mcp` `terminal` `single-binary` `cross-platform`

### P0-3　无 profile README

`raine-x` 账号下有 5 个仓库（CodeForge 3★ / CodeForge-GO 2★ / codeforge-mobile 1★ /
OpenRender 1★ / AutoGLM-For-Android 0★），但**没有一个是 profile README**。

面试官点进你的主页，看到的是一排孤立的仓库名。

**动作：** 建 `raine-x/raine-x` 仓库，README 写个人定位 + 项目列表 + 技术栈。
一个 profile README 的效果通常大于在单个仓库里再优化十行。

## 三、P1 —— 技术深挖会暴露的问题

### P1-1　`s.cfg` 是全仓库唯一无锁的共享可变状态

**证据：** `pkg/server/server.go:51-52`，`Server` 结构体持有裸指针：
```go
type Server struct {
    cfg      *config.Config   // ← 无锁
    ...
    shutdownMu sync.Once      // 只有这一个锁，管的是关闭不是配置
    termuxState atomic.Int32
}
```
- **23 处无锁写**：`api_handlers.go:69,180,182`；`appearance.go:56,66,76,86,253`；
  `builtin_plugins_handler.go:41-51,144`；`subagents_handler.go:46-71`；
  `workspace.go:90,211`
- **92 处读**，跨 HTTP handler goroutine 与 WS 读循环 goroutine
- `api_handlers.go:113` 的 `next := *s.cfg` 是**结构体整体浅拷贝**，
  而 `Config` 内含 `*bool`（`config/config.go:63-71,181-199`）与切片（`:156,110`）
- `api_handlers.go:903` 的 `kept := s.plugins[:0]` **原地截断复用底层数组**

**对比：** `pkg/agent` 已有成熟分层锁（`rtMu` / `h.mu` / `Session.mu`）且锁序被文档化
（`pkg/agent/history.go:368-369`）。**`pkg/server` 完全没有继承这套治理。**

**动作：** `Server` 加 `cfgMu sync.RWMutex` + `cfgSnapshot()` 读法（与 agent 层同构）；
`Config.SaveState()`（`config/state.go:205-215`）用 `os.WriteFile` **非原子写**，
并发调用会互相截断 → 改成 temp file + rename。

> 详细的架构分析见 [对标分析报告](对标分析报告.md)。

### P1-2　命令黑名单可绕过

`pkg/security/policy.go:33` 的正则末尾 `\s*$` 锚定让 `rm -rf / ; echo done`、
`rm -r -f /`、`bash -c 'rm -rf /'` 全部绕过。默认 `ask` 模式有审批兜底，
但 `auto` 档会全部放行。

**动作：** 去末尾锚定 + 补常见绕过形态 + `auto` 档对高危前缀强制 Ask。

### P1-3　License 表述不清

`license: NOASSERTION` —— 因为 `LICENSE` 是 **GPL-3.0 + 自定义附加条款**（`LICENSE:5-7`）。
`README.md` 的许可章节现在已写明「非标准 SPDX 许可」，但 GitHub 侧仍识别不出。

**这不是 bug，是产品决策**（GPL-3.0 本身允许商用，你主动加了限制）。
**动作：** GitHub 设置里改用自定义 License，或在仓库简介注明；
面试时准备一段话解释"允许使用但禁止商用"的取舍——**这个话题本身是加分项**，
说明你懂 copyleft 与宽松许可的差别。

### P1-4　README 缺架构图与 demo 动图

README 已重构为功能演示（150 行，12 个功能域），但：
- `mermaid` 出现 **0 次** —— 技术岗面试常问"讲讲你的架构"，现在只能靠嘴说
- 截图与动图是**占位块**（`<!-- GIF:APPROVAL -->` 等），**还没补实际素材**
- 三个占位里，**审批弹窗动图价值最高**——它是"AI 编码智能体"最核心的差异化交互

**动作：** 加一张 ReAct 循环 + 工具执行 + 存储的流程图；补审批弹窗与 diff 预览动图。
`test/shot_*.mjs` 脚本可改造成自动录制。

### P1-5　提交信息规范刚立，尚未贯彻

新规范（`AGENTS.md` §GIT）已写入：**首行中文概括 + 正文分条 + 不加 `fix:` 前缀**。

但历史上近 30 条里 **23 条只有标题没有正文**，且有 `优化GUI表现`、`阶段性修复`
这类无法理解的记录。**提交历史本身就是项目文档**——76 次提交里有多少能被面试官读懂，
直接影响观感。

已有的 7 条好例子（`fix(builtin): 撤销还原无锁写文件系统，且用裸 os.WriteFile 破坏原子性`）
说明能力是有的，只是没贯彻。**新提交已按规范执行**（本次会话的提交都是）。

### P1-6　版本命名不统一

7 个 tag：`v0.0.2` ~ `v0.1.0` + `预览版`。GitHub 上 1 个 Release 叫"预览版"。
**动作：** 统一 SemVer，README 引用最新版本号。

## 五、求职叙事建议（把技术亮点变成能被听懂的卖点）

代码里的硬活很扎实，但**现在都藏在注释里，面试官不会去翻**。建议主动准备：

### 1. 工作区围栏与软链越界防护
`pkg/tools/builtin` + `pkg/backend` 的分层设计：Backend 只做纯 IO，
围栏判断只在 `FS.checkScope` 一份。`AGENTS.md` §5 明确记录了三条决策
（`pathLocks` 不下沉、撤销副本不进 Backend、`Backend` 不加 `IsInScope`），
**"我知道为什么不这么设计"比"我这么设计了"值钱得多**。

### 2. 概率性并发护栏
`pkg/tools/builtin/undo_session_race_test.go:14-38` 的注释是一份优秀的工程说明：
讲清了缺陷、窗口宽度、为什么是概率性的、确定性保护来自哪里。
这种测试在真实项目里很少见，**值得单独讲 3 分钟**。

### 3. 结构化断言代替竞态检测
`go test -race` 需要 cgo，而项目要求 `CGO_ENABLED=0` 静态编译。
于是用 AST 解析源码做分层断言（`pkg/tools/builtin/layering_test.go`）
——**"内置工具里禁止直接调 os.*/exec.*"由测试强制**。
这是把约束编码进测试的思路，比覆盖率数字有说服力。

### 4. 跨端差异的真正处理
Termux 适配不是"顺便能跑"：shell 探测、存储授权、内置目录选择器、
进程组管理、`GOMEMLIMIT` 按物理内存 25%。**"同一个二进制在安卓手机上跑"**
是个有传播性的故事，比"我用了 Go"强得多。

### 5. 零构建前端 + 零运行时依赖
手写单文件 JS + `go:embed` + `CGO_ENABLED=0`，最终产出 16 MB 单文件。
**"部署只需要拷贝一个文件"** 是能一句话说清且让人记住的价值。

### 6. 上下文工程（对标 Claude Code 的杀手锏）
在线校准 + 压缩状态落盘 + 压缩永不丢历史 + 大结果无损外置。
详见 [对标分析报告](对标分析报告.md) 第六节。
